# External services

The site is static, so everything that is not plain HTML/CSS/JS is handled by four external services.
This document explains what each one does, how it is configured, and where its keys live.
For the code itself see [CODE.md](CODE.md).

| Service | Used for | Cost | Dashboard |
|---|---|---|---|
| [TinaCMS / Tina Cloud](#tinacms--tina-cloud) | Content editor at `/admin` | Free plan | https://app.tina.io |
| [GitHub Pages + Actions](#github-pages--github-actions) | Hosting and automatic deploys | Free | Repo → Settings / Actions |
| [EmailJS](#emailjs) | Sending the contact form by e-mail | Free plan: 200 e-mails/month | https://dashboard.emailjs.com |
| [Google reCAPTCHA v2](#google-recaptcha-v2) | "No soy un robot" checkbox on the form | Free | https://www.google.com/recaptcha/admin |

Live site: https://mariasuevos.github.io/estudio-rupit/ · Editor: https://mariasuevos.github.io/estudio-rupit/admin/

## Where the keys live

The same variables are set in two places: `.env` for local development (git-ignored, template in
[`.env.example`](../.env.example)) and GitHub for production (**repo → Settings → Secrets and variables → Actions**).
The deploy workflow passes them to the build.

| Variable | Service | In GitHub as | Public in the built site? |
|---|---|---|---|
| `TINA_CLIENT_ID` | Tina Cloud | Secret | Yes (the admin needs it) |
| `TINA_TOKEN` | Tina Cloud (read-only token) | Secret | Used only at build time |
| `TINA_BRANCH` | Tina Cloud | Set to `main` in the workflow | — |
| `VITE_EMAILJS_SERVICE_ID` | EmailJS | Secret | Yes |
| `VITE_EMAILJS_TEMPLATE_ID` | EmailJS (template with copy to sender) | Secret | Yes |
| `VITE_EMAILJS_TEMPLATE_ID_NO_COPY` | EmailJS (template without copy) | Secret | Yes |
| `VITE_EMAILJS_PUBLIC_KEY` | EmailJS | Secret | Yes |
| `VITE_EMAILJS_SEND_COPY` | EmailJS (`true` / `false`) | **Variable** (not secret) | Yes |
| `VITE_RECAPTCHA_SITE_KEY` | reCAPTCHA | Secret | Yes |
| `BASE_PATH` | Vite / Tina | Set to `/estudio-rupit/` in the workflow | — |

Anything starting with `VITE_` is embedded in the JavaScript sent to visitors, so it is **not secret** by design:
EmailJS public key, template IDs and the reCAPTCHA site key are meant to be public. They are stored as GitHub
secrets only for tidiness. Real protection comes from the domain restrictions and the reCAPTCHA check described
below. Never put the **reCAPTCHA secret key** in `.env` or GitHub: it belongs only in EmailJS.

`VITE_*` values are read at **build time**. After changing one in GitHub, re-run the deploy workflow.

## TinaCMS / Tina Cloud

TinaCMS gives non-technical editors a visual editor at `/admin` for the JSON files in `content/` and the media in
`public/uploads/`. Tina Cloud handles login and, when someone saves, **commits the change to the GitHub repo**.
That commit triggers a new deploy, so changes are live after a couple of minutes.

### How it is configured

- **Schema**: [`tina/config.ts`](../tina/config.ts). One collection per content file (*Ajustes del sitio*,
  *Inicio*, *Sobre rupit*, *Servicios*, *Proyectos*, *Contacto*) plus *Páginas* (`content/pages/`, one file per page).
  Single-file collections cannot be created or deleted from the editor. Field labels and help texts are in Spanish
  for the editors.
- **Credentials**: `clientId` and `token` come from `TINA_CLIENT_ID` / `TINA_TOKEN`. Without them Tina runs in local
  mode (`npm run dev`), saving straight to disk.
- **Branch**: `TINA_BRANCH` (`main`).
- **Admin output**: built into `public/admin/` (git-ignored) and served at `/admin`, under `BASE_PATH`.
- **Media**: stored in `public/uploads/` (`mediaRoot: "uploads"`). Tina saves paths as `/uploads/…`; the site adds
  the base path automatically.
- `tina/tina-lock.json` is generated by Tina and committed; `tina/__generated__/` is git-ignored.

### Setup (already done, kept for reference)

1. At https://app.tina.io, create a project from the GitHub repo `mariasuevos/estudio-rupit`, branch `main`.
2. Site URLs: `https://mariasuevos.github.io/estudio-rupit` and `http://localhost:5173`.
3. Copy the **Client ID** and create a **read-only token**; save them as the `TINA_CLIENT_ID` and `TINA_TOKEN`
   GitHub secrets (and in `.env` to run `npm run build` locally).
4. Invite the editors from the Tina Cloud project (*Collaborators*).

### Notes

- Editors need a Tina Cloud account invited to the project; they do not need GitHub access.
- If the schema changes (`tina/config.ts`), push it to `main` before editors use the new fields.
- If the build fails with a Tina error, check that the token is still valid and that the schema in `main` matches
  the one Tina Cloud has indexed (Tina Cloud → project → *Configuration*).

## GitHub Pages + GitHub Actions

### How it is configured

- **Repo settings → Pages → Source: "GitHub Actions".**
- Workflow: [`.github/workflows/deploy.yml`](../.github/workflows/deploy.yml). It runs on every push to `main`
  (including Tina's commits) and from the *Run workflow* button in the Actions tab:
  1. checks out the repo and installs Node 26 + dependencies (`npm ci`);
  2. runs `npm run build` with the Tina credentials, `BASE_PATH=/estudio-rupit/` and all `VITE_*` variables;
  3. uploads `dist/` and publishes it to GitHub Pages.
- Only one deploy runs at a time; a newer push cancels the one in progress.
- Direct links to inner pages work because the build creates one `index.html` per page plus a `404.html`
  (see [CODE.md → Build details](CODE.md#build-details-viteconfigts)).

### Redeploy manually

GitHub → repo → **Actions → "Deploy to GitHub Pages" → Run workflow**. Needed after changing a secret or variable.

### Moving to a custom domain (e.g. estudiorupit.com)

1. GitHub → Settings → Pages → *Custom domain*, and set the DNS records GitHub asks for.
2. In `deploy.yml`, change `BASE_PATH` from `/estudio-rupit/` to `/`.
3. In Tina Cloud, update the Site URL.
4. In EmailJS and reCAPTCHA, add the new domain to the allowed domains.

## EmailJS

The contact form (`/contacto`) sends e-mails straight from the browser through EmailJS, so no server is needed.
Code: [`src/lib/email.ts`](../src/lib/email.ts) and [`src/pages/ContactPage.tsx`](../src/pages/ContactPage.tsx).

### How it is configured

1. **Email Services**: a Gmail (or other) service connected to the account that sends the e-mails →
   `VITE_EMAILJS_SERVICE_ID`.
2. **Email Templates**: the main template → `VITE_EMAILJS_TEMPLATE_ID`.
   - **To Email**: the studio address that receives the requests (the recipient is set here, not in the code).
   - **Reply To**: `{{email}}`, so replying answers the person who wrote.
   - **Subject**: `Nueva solicitud: {{nombres}}`
   - **Content**: uses the form variables `{{nombres}}`, `{{email}}`, `{{fecha}}`, `{{lugar}}`, `{{necesidad}}`,
     `{{dudas}}`.
   - **Settings → reCAPTCHA V2 verification**: enabled, with the reCAPTCHA *secret* key.
3. **Account → General**: the *Public Key* → `VITE_EMAILJS_PUBLIC_KEY`.
4. **Account → Security**: allowed domains (`mariasuevos.github.io`, `localhost`), rate limit enabled, and
   *"Allow EmailJS API for non-browser applications"* kept **disabled**.

### Copy to the sender (two templates)

EmailJS sends a copy to the person who fills in the form through its **Auto-Reply** feature, which is attached to a
template. So there are two identical templates:

| Template | Auto-Reply | Variable | Selected when |
|---|---|---|---|
| Main | On | `VITE_EMAILJS_TEMPLATE_ID` | `VITE_EMAILJS_SEND_COPY=true` (default) |
| Twin | Off | `VITE_EMAILJS_TEMPLATE_ID_NO_COPY` | `VITE_EMAILJS_SEND_COPY=false` |

Both must keep reCAPTCHA enabled. If `SEND_COPY=false` and the twin ID is missing, the form will not send (a warning
appears in the browser console). If any of the three main variables is missing, the form shows the error message.

> **Known issue:** with `VITE_EMAILJS_SEND_COPY=true` the Auto-Reply copy currently arrives at the studio inbox
> (a duplicate) instead of at the sender. EmailJS sends the Auto-Reply to the address configured in the
> templates, and the sender's address is only set in *Reply To*, not in *From* / *To*. Keep `SEND_COPY=false` until
> the Auto-Reply template is fixed to send to `{{email}}`, then test it with a personal address.

### Changing the form fields

The field names are the template variables, so a new field needs changes in the code (`FIELDS` in `ContactPage.tsx`,
`ContactMessage` in `email.ts`, the `fields` list in `tina/config.ts`) **and** in both EmailJS templates.

## Google reCAPTCHA v2

The "No soy un robot" checkbox on the contact form. Code: [`src/components/Recaptcha.tsx`](../src/components/Recaptcha.tsx).

### How it is configured

- Key type: **reCAPTCHA v2 → "I'm not a robot" Checkbox**, created at https://www.google.com/recaptcha/admin.
- Domains: `mariasuevos.github.io` and `localhost` (add the custom domain if there is one).
- **Site key** → `VITE_RECAPTCHA_SITE_KEY` (public, used by the browser).
- **Secret key** → only in EmailJS (each template → *Settings* → *Enable reCAPTCHA V2 verification*).

### How it works

1. The component loads Google's script only on the contact page, in Spanish (`hl=es`).
2. When the visitor ticks the box, Google returns a one-time token.
3. The token is sent to EmailJS as `g-recaptcha-response`; EmailJS verifies it with the secret key and refuses to send
   otherwise. So even someone who copies the public EmailJS keys cannot send e-mails without solving the captcha.
4. After each attempt the checkbox is reset, because a token can only be used once.

Without `VITE_RECAPTCHA_SITE_KEY` the checkbox is not shown and the form sends without it. **If the site key is
removed, also disable reCAPTCHA in the EmailJS templates**, or every submission will be rejected.

## Anti-spam measures

Besides reCAPTCHA and the EmailJS security settings, the form itself ([`ContactPage.tsx`](../src/pages/ContactPage.tsx)):

- **Honeypot**: a hidden `website` field that only bots fill in; those submissions are silently ignored.
- **Minimum time**: submissions less than 3 seconds after opening the page are ignored.
- **Maximum length** per field (120 characters for name and e-mail, up to 3000 for the text areas).
- **Duplicate blocking**: an identical request already sent from the same browser is not sent again (stored in
  `localStorage`, last 20 requests); the visitor sees the *duplicate* message instead.
- **Double-click protection** while a request is being sent.

## Troubleshooting

| Symptom | Likely cause |
|---|---|
| Form always shows the error message | Missing `VITE_EMAILJS_*` variable in the build, wrong ID, domain not allowed in EmailJS, or reCAPTCHA enabled in EmailJS but no site key on the site. Check the browser console. |
| Captcha box does not appear | `VITE_RECAPTCHA_SITE_KEY` missing in the build, or the current domain is not in the reCAPTCHA key's domains |
| Edits in `/admin` do not appear on the site | The deploy is still running or failed: check the Actions tab |
| `/admin` asks to log in but rejects the user | The user is not invited in the Tina Cloud project |
| Deploy fails in the "build" step | Usually Tina: expired token or schema out of sync. Read the workflow log |
| Changed a secret but nothing changed | `VITE_*` values are read at build time: re-run the workflow |
| E-mails stop arriving mid-month | EmailJS free plan limit (200/month) reached |
